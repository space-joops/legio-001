77장의 배열을 실제로 보여 주고, 손가락으로 넘기게 하는 부분입니다.

다루는 파일: `src/components/RosaryGuide.tsx` · `RosaryStepView.tsx` · `src/hooks/useSwipe.ts` · `RosaryGuide.module.css`

## 2. 상태 6개

```tsx
const [mysteryId, setMysteryId] = useState<MysteryId | null>(null);
const [index, setIndex] = useState(0);
const [asking, setAsking] = useState(false);
const [recorded, setRecorded] = useState(false);
const [slideDirection, setSlideDirection] = useState<"left" | "right">("right");
const [fullScreenImage, setFullScreenImage] = useState<{...} | null>(null);
```

| 상태 | 담는 값 | 언제 바뀌나 |
|---|---|---|
| `mysteryId` | 오늘의 신비 | 마운트 직후 딱 한 번 |
| `index` | 지금 몇 번째 화면 (0~76) | 넘길 때마다 |
| `asking` | "5단 기록할까요?" 확인창 표시 여부 | 마지막에서 다음을 누를 때 |
| `recorded` | "기록했습니다" 안내문 표시 여부 | 기록한 뒤 |
| `slideDirection` | 다음 화면이 어느 쪽에서 들어올지 | 넘기는 방향에 따라 |
| `fullScreenImage` | 성화 팝업 내용. `null`이면 닫힘 | 성화를 누를 때 |

> **`useState` vs `useRef` 판단 기준**: "이 값이 바뀌면 화면을 다시 그려야 하나?"
> 그렇다면 `useState`, 아니면 `useRef`. 아래 ref 들이 후자입니다.

## ref 3개

```tsx
const rootRef = useRef<HTMLElement>(null);      // 최상위 <section>. 스크롤 되돌리기용
const contentRef = useRef<HTMLDivElement>(null); // 손가락을 따라 움직이는 요소
const initRef = useRef(false);                   // "이미 한 번 했다" 표시
```

`contentRef` 가 state 가 아닌 이유가 특히 중요합니다. 손가락을 따라오는 애니메이션은 1초에 수십 번 값이 바뀝니다. state 로 다루면 **그때마다 화면 전체를 다시 그리게 되어** 심하게 버벅입니다. 그래서 DOM 의 `style` 을 직접 만집니다.

## 3. useEffect 5개

### (1) 오늘의 신비 정하기 — `[]`

```tsx
useEffect(() => {
  setMysteryId(getMysteryIdForDate(new Date()));
}, []);
```

`[]` 는 "붙은 뒤 딱 한 번". 왜 여기서 하는지는 [01-데이터 §5](01-데이터.md#5-요일--신비) 참고.

### (2) 이어서 바칠 위치로 점프 — `[steps, progress]`

```tsx
const initRef = useRef(false);
useEffect(() => {
  if (steps.length > 0 && progress > 0 && !initRef.current) {
    const targetDecade = progress + 1;                              // 3알 채웠으면 4단
    const targetIndex = steps.findIndex((s) => s.decade === targetDecade);
    if (targetIndex !== -1) setIndex(targetIndex);
    initRef.current = true;
  }
}, [steps, progress]);
```

구슬을 3알 채워 둔 채로 창을 열면 **4단 신비 선포 화면(인덱스 48)부터** 시작합니다. 이미 바친 3단을 다시 넘겨 가며 지나칠 이유가 없기 때문입니다.

`initRef` 가 없으면 어떻게 될까요? 기록을 마치면 `progress` 가 0으로 돌아가는데, 그때 이 effect 가 또 돌아서 화면이 멋대로 튑니다. **한 번만 하고 끝내는 표시**가 필요한 것입니다.

`useState` 가 아니라 `useRef` 인 이유: 이 플래그가 바뀐다고 화면을 다시 그릴 필요가 없습니다.

### (3) 넘길 때마다 스크롤 되돌리기 — `[index]`

```tsx
useEffect(() => {
  rootRef.current?.scrollIntoView({ block: "start" });
}, [index]);
```

긴 기도문을 아래까지 읽고 넘겼는데 새 화면도 아래쪽부터 보이면 곤란합니다. 따라 바치는 화면이니 항상 제목이 맨 위에 와야 합니다.

### (4) 오늘의 신비를 부모에게 올려 보내기 — `[mysteryId, onContextChange]`

```tsx
useEffect(() => {
  if (!onContextChange) return;
  if (!mysteryId) { onContextChange(null); return; }
  onContextChange(getMysteryShortHeading(mysteryId));
}, [mysteryId, onContextChange]);
```

오늘의 신비는 가이드 안이 아니라 **창 제목 라인**("묵주기도 · 영광의 신비(수·일)")에 표시됩니다. 제목은 `PrayerTextDialog` 가 그리므로 이 콜백으로 알려 줍니다. 한 줄에 들어가야 해서 `getMysteryShortHeading` 이 요일을 축약합니다("(수요일·일요일)" → "(수·일)"). 몇 번째 단인지는 묵상 문장의 "N." 번호(`step.meditation`)가 알려 주므로 제목에는 넣지 않습니다.

`onContextChange` 에는 부모(`CounterGrid`)가 `setState` 함수를 **그대로** 넘깁니다. 인라인 화살표 함수를 넘기면 매 렌더마다 새 함수가 되어 이 effect 가 계속 다시 돕니다.

### (5) 닫힐 때 제목 청소 — `[onContextChange]`

```tsx
useEffect(() => () => onContextChange?.(null), [onContextChange]);
```

창을 닫으면 가이드가 언마운트되는데, 그때 제목에 "고통의 신비 …" 가 남아 있으면 다음에 다른 기도문 창을 열 때 어색합니다. 클린업 함수에서 `null` 로 되돌립니다.

## 4. useMemo — 77장을 언제 다시 만드나

```tsx
const steps = useMemo(
  () => mysteryId ? buildRosarySteps(mysteryId, language, { creed: t("rosary.creed"), ... }) : [],
  // eslint-disable-next-line react-hooks/exhaustive-deps
  [mysteryId, language]
);
```

의존성이 `[mysteryId, language]` 뿐입니다. **`t` 가 빠져 있는 게 핵심**입니다.

`t` 는 렌더할 때마다 새로 만들어지는 함수라, 의존성에 넣으면 **매 렌더마다 77장을 다시 만듭니다.** 그러면 `useMemo` 를 쓰는 의미가 사라집니다. 문구를 실제로 바꾸는 것은 `language` 이므로 그것만 봅니다.

ESLint 는 "의존성이 빠졌다"고 경고하므로 `eslint-disable` 로 끄고, 바로 위에 이유를 적어 둡니다. **이 저장소에서 `eslint-disable` 에는 항상 이유를 적는 것이 규칙입니다.**

## 5. 스와이프의 수학

`src/hooks/useSwipe.ts` 하나에 다 들어 있습니다.

### 좌표 두 개만 기억한다

```ts
const start = useRef<Point | null>(null);   // 손가락이 처음 닿은 곳
const end = useRef<Point | null>(null);     // 마지막으로 지나간 곳
```

### 손가락을 뗐을 때의 판정

```ts
const distanceX = start.current.x - end.current.x;
const distanceY = start.current.y - end.current.y;
```

```
   손가락을 왼쪽으로 밀면            손가락을 오른쪽으로 밀면
   start.x = 300, end.x = 200       start.x = 100, end.x = 250
   distanceX = +100                 distanceX = -150
        → 다음 화면                       → 이전 화면
```

**부호가 헷갈리기 쉽습니다.** `시작 - 끝` 이므로 왼쪽으로 밀면 **양수**입니다.

판정은 세 단계입니다.

```ts
// ① 움직임이 없었으면 그냥 탭 → 무시 (버튼이나 링크를 누른 경우)
if (!start.current || !end.current) return;

// ② 세로로 더 많이 움직였으면 스크롤이지 스와이프가 아님
if (Math.abs(distanceX) <= Math.abs(distanceY)) return;

// ③ 임계값을 넘겼는가
if (distanceX > SWIPE_THRESHOLD_PX) onSwipeLeft();        // 다음
else if (distanceX < -SWIPE_THRESHOLD_PX) onSwipeRight(); // 이전
```

②를 그림으로 보면:

```
        │                    스와이프로 인정되는 영역
        │   ╲            ╱
   세로 │     ╲        ╱
   이동 │       ╲    ╱
        │         ╲╱          ← |dx| = |dy| 대각선
        │         ╱╲
        │       ╱    ╲
        └──────────────────── 가로 이동
```

대각선보다 가로로 더 기울어야 스와이프입니다.

### 임계값

```ts
export const SWIPE_THRESHOLD_PX = 50;
```

- 너무 작으면: 세로로 스크롤하다 손가락이 조금만 비뚤어져도 화면이 넘어감
- 너무 크면: 넘기려고 해도 안 넘어감

**속도(velocity)는 보지 않습니다.** 거리만 봅니다. 천천히 확실하게 미는 어르신 사용자에게 속도 기준은 오히려 불리하기 때문입니다.

### 손가락 따라오기

밀고 있는 동안 화면이 손가락을 따라옵니다.

```ts
// touchstart — 전환 효과를 꺼서 즉시 붙게 한다
contentRef.current.style.transition = "none";

// touchmove — 가로로 더 많이 움직였을 때만 따라간다
if (Math.abs(distanceX) > distanceY) {
  contentRef.current.style.transform = `translateX(${-distanceX}px)`;
}

// touchend — 제자리로 되돌린다
contentRef.current.style.transition = "transform 0.3s ease";
contentRef.current.style.transform = "translateX(0)";
```

넘어가는 경우에는 새 화면이 통째로 갈아 끼워지므로 이 "제자리 복귀"는 눈에 보이지 않습니다.

### CSS 쪽 협력

```css
.guide {
  touch-action: pan-y;   /* 세로 스크롤만 브라우저에 넘기고 가로는 우리가 가져온다 */
}
.contentWrapper {
  overflow-x: hidden;    /* 따라오다 삐져나온 부분을 감춘다 */
}
```

`touch-action: pan-y` 가 없으면 옆으로 쓰는 동안 브라우저가 페이지를 가로로 끌어 버립니다. `preventDefault()` 를 부르는 대신 CSS 로 해결하는 방식입니다.

### 지금 없는 것

- **마우스 드래그** — PC 에서는 화살표 버튼으로만 이동합니다
- **키보드 좌우 화살표** — 없습니다
- **`onTouchCancel`** — 전화가 오는 등으로 제스처가 취소되면 인라인 `transform` 이 남을 수 있습니다 ([연습문제 중급 7번](05-연습문제.md))

## 6. 훅 순서 규칙 — 걸려 넘어지기 쉬운 곳

`RosaryGuide.tsx` 에는 이런 조기 반환이 있습니다.

```tsx
if (!mysteryId || steps.length === 0) return null;
```

그리고 `useSwipe` 는 **이 줄보다 위**에 있어야 합니다.

```tsx
const swipeHandlers = useSwipe({ ... });   // ← 반드시 여기

if (!mysteryId || steps.length === 0) return null;   // ← 조기 반환은 그 다음
```

React 의 규칙은 **"훅은 매 렌더에서 같은 순서로 같은 개수만큼 불려야 한다"** 입니다. `useSwipe` 안에도 `useRef` 가 두 개 들어 있으므로, 조기 반환 아래로 내리면 "어떤 렌더에서는 불리고 어떤 렌더에서는 안 불리는" 훅이 되어 React 가 상태를 엉뚱한 곳에 연결합니다.

> 파이썬에는 대응 개념이 없어 특히 낯선 규칙입니다. React 는 훅을 **호출 순서**로 식별하기 때문에 순서가 흔들리면 안 됩니다.
> ESLint 의 `react-hooks/rules-of-hooks` 가 이걸 잡아 주므로 `npm run lint` 를 믿으세요.

## 7. `key` 로 애니메이션 다시 재생시키기

이 코드베이스에서 가장 "트릭" 같은 부분입니다.

```tsx
<div ref={contentRef} key={index} className={`${styles.contentWrapper} ${slideIn...}`}>
```

`key` 가 바뀌면 React 는 그 요소를 **고치는 게 아니라 버리고 새로 만듭니다.**

왜 그래야 할까요? CSS `animation` 은 **요소가 생길 때 한 번** 재생됩니다. 요소를 재사용하면 클래스가 그대로라 다시 재생되지 않습니다. `key={index}` 를 주면 화면을 넘길 때마다 새 요소가 생기므로 슬라이드가 매번 새로 뜁니다.

같은 기법이 제목에도 쓰입니다(`RosaryStepView.tsx`).

```tsx
<p key={stepIndex} className={styles.heading}>
```

`.heading` 에는 깜박임 애니메이션이 걸려 있는데, 성모송처럼 **제목 글자가 같으면** React 가 노드를 그대로 재사용해 깜박임이 안 뜁니다. `key` 로 강제 교체해서 해결합니다.

```css
.heading {
  /* 세 번 깜박이고 멈춘다. 500ms 주기 = 초당 2회.
     초당 3회를 넘는 깜박임은 광과민성 발작 위험이 있어 접근성 지침이 금지한다. */
  animation: blink 500ms ease-in-out 3;
}
```

덤: 스와이프 중에 인라인으로 넣어 둔 `transform` 도 새 요소에서는 깨끗이 사라집니다.

## 8. 슬라이드 방향

```tsx
const handleNext = () => { setSlideDirection("right"); setIndex(index + 1); };
const handlePrev = () => { setSlideDirection("left");  setIndex(index - 1); };
```

```css
.slideInRight { animation: slideInRight 0.3s ease-out forwards; }

@keyframes slideInRight {
  from { opacity: 0; transform: translateX(20px); }   /* 오른쪽에서 */
  to   { opacity: 1; transform: translateX(0); }      /* 제자리로 */
}
```

`transition` 이 아니라 `animation` 인 이유는 §7 과 같습니다 — "값이 변했다"가 아니라 "새 요소가 생겼다"에 반응해야 하기 때문입니다.

## 9. 화면 한 장 — RosaryStepView

자기 상태가 하나도 없습니다. 받은 것을 그리기만 합니다.

```tsx
<div className={styles.stickyHead}>
  {step.meditation && <p className={styles.meditation}>{step.meditation}</p>}
  <div className={styles.headingRow}>            {/* [◀] 이름 [▶] 3칸 그리드 */}
    {onPrev ? <button className={styles.stepArrow} onClick={onPrev} …>◀</button> : <span />}
    <p key={stepIndex} className={styles.heading}>
      {step.title}
      {step.ordinal && <span className={styles.ordinal}>{step.ordinal}</span>}
    </p>
    {onNext ? <button className={styles.stepArrow} onClick={onNext} …>▶</button> : <span />}
  </div>
</div>

{step.image && ( <img src={step.image} onClick={onImageClick} … /> )}

{step.lines.length > 0 && (
  <div className={styles.body}>
    {step.lines.map((line, i) => <p key={i} className={styles.line}>{line}</p>)}
  </div>
)}
```

`.stickyHead` 는 `position: sticky` 라 긴 기도문이 아래로 흘러가도 제목이 화면 위에 붙어 있습니다.

맨 위의 `step.meditation` 은 그 단의 묵상 문장("1. 예수님께서 부활하심을 묵상합시다")입니다. 앞의 "1." 이 몇 번째 단인지 알려 줍니다. 단 안의 모든 화면(주님의 기도·성모송×10·영광송·구원 기도)에 붙어 있어서, 성모송을 세는 중에도 무엇을 묵상하는지 잊지 않게 합니다. 시작·마침 기도와 신비 선포 화면에는 없습니다 — 선포 화면은 제목 자체가 이 문장입니다. 자세한 것은 [01-데이터 §4](01-데이터.md#4-rosarystep--화면-한-장의-모양).

오늘의 신비("영광의 신비(수·일)")는 이 컴포넌트가 아니라 창 제목 라인이 보여 줍니다 — [§3의 effect (4)](#3-useeffect-5개) 참고.

기도 이름(`heading`)과 창 제목에는 `useFitLine`(src/hooks/useFitLine.ts)이 붙어 있습니다 — 글자 크기 설정을 키워 칸을 넘치면 폰트를 1px씩 줄여 한 줄을 지키고, 최소 크기(1rem)로도 안 들어가는 긴 문장은 원래 크기로 되돌려 줄바꿈을 허용합니다.

### 좌우 화살표

이전/다음 화살표는 기도 이름 **양끝**에 붙습니다. `.headingRow` 가 `화살표 | 이름 | 화살표` 3칸 그리드이고, 이름이 가운데 칸에서 중앙 정렬됩니다. 화살표는 일부러 수수하게(배경·테두리 없는 삼각형만) 두었습니다 — 기도문이 주인공인 화면이기 때문입니다. 터치 영역은 `--min-tap-target` 으로 넉넉합니다.

- 핸들러는 `RosaryGuide` 가 `onPrev`/`onNext` prop 으로 넘깁니다. **안 넘기면 화살표 대신 같은 폭의 빈 칸**을 그려 이름이 좌우로 흔들리지 않습니다.
- 첫 화면(`index === 0`)에서는 ◀ 자리가 빈 칸입니다.
- 확인창(`asking`)이 떠 있는 동안에는 둘 다 빈 칸입니다 — 스와이프가 막히는 것과 같은 이유입니다.
- 확인창은 마지막 화면의 긴 성모찬송 아래에 생기므로, 뜨는 순간 `scrollIntoView` 로 화면 안에 데려옵니다(§3 참고).

## 10. 마지막 화면과 기록

```tsx
const handleNext = () => {
  if (isLast) {          // 77번째에서는 더 갈 곳이 없다
    setAsking(true);     // 대신 "5단을 기록할까요?"
    return;
  }
  ...
};

const handleConfirm = () => {
  onRecordSet();     // → 부모 → useCurrentReport.addRosarySet → +5
  setAsking(false);
  setRecorded(true);
  setIndex(0);       // 처음으로 되돌려 다음 5단을 이어서 바칠 수 있게
};
```

확인창은 **중첩 `<dialog>` 가 아니라 그 자리에 그냥 그립니다.** 이미 열려 있는 창(`PrayerTextDialog`) 안에 모달을 또 띄우는 것보다, 같은 흐름의 한 단계로 보여 주는 편이 안전하기 때문입니다.

확인창이 떠 있는 동안에는 스와이프도 막힙니다(`enabled: !asking`). "기록할까요?"를 읽는 중에 손가락이 스치는 것만으로 화면이 넘어가면 곤란합니다.
