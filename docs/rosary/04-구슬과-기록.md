# 04. 구슬과 기록 — 숫자가 흘러가는 길

묵주기도를 몇 단 바쳤다는 숫자가 어디서 만들어져서 어디까지 가는지 추적합니다. JSX 가 거의 없어 읽기 편한 장입니다.

다루는 파일: `src/hooks/useCurrentReport.ts` · `src/components/CounterButton.tsx` · `src/lib/prayerSubmission.ts`

---

## 1. 왜 구슬인가

다른 카운터 4종은 탭 한 번에 숫자가 1씩 오릅니다. 묵주기도만 다릅니다.

```
탭 1회 → ● ○ ○ ○ ○   숫자 그대로
탭 2회 → ● ● ○ ○ ○   숫자 그대로
탭 3회 → ● ● ● ○ ○   숫자 그대로
탭 4회 → ● ● ● ● ○   숫자 그대로
탭 5회 → ○ ○ ○ ○ ○   숫자 +5 ★
```

묵주기도는 **5단을 한 묶음으로** 바치기 때문입니다. 3단만 바치고 마는 일은 없으니, 세다 만 것을 보고서에 올리지 않으려는 설계입니다.

이 규칙을 만드는 건 설정 한 줄입니다.

```ts
// src/lib/constants.ts
export const ROSARY_SET_SIZE = 5;

export const PRAYER_ITEMS: PrayerItemConfig[] = [
  ...
  { key: "rosaryDecades", ..., setSize: ROSARY_SET_SIZE },   // ← 5종 중 이것만 setSize 를 가짐
  ...
];
```

`setSize` 가 있는 항목만 구슬 줄이 그려지고, 탭이 숫자 대신 구슬을 채웁니다.

## 2. 저장되는 모양

```ts
// src/lib/types.ts 의 WeeklyReport
counts: {
  weekdayMass: 3,
  priestPrayer: 5,
  chainPrayer: 2,
  rosaryDecades: 15,    // ← 실제 기록된 단 수 (5의 배수)
  aspirations: 40,
},
rosarySetProgress?: 3,  // ← 지금 채워 둔 구슬 (0~4)
```

**`rosarySetProgress` 가 `counts` 안이 아니라 형제 필드인 게 중요합니다.**

`counts` 안에 넣었다면 `PRAYER_ITEMS` 를 순회하는 모든 곳에 열이 하나 더 생겼을 것입니다.

```
월례 보고서의 기도 표      →  공식 양식에 없는 열이 생김
교구 지시사항 줄           →  "구슬 3개" 라는 이상한 항목
LEGIO1 서기 전송 payload   →  형식이 바뀌어 옛 메시지 해석이 깨짐
```

공식 양식에는 그런 칸이 없습니다. 그래서 일부러 밖에 두었습니다.

> `rosarySetProgress` 는 **선택 필드(`?`)** 입니다. 이 기능이 생기기 전에 저장된 보고서에는 아예 없습니다. 그래서 읽을 때는 **항상 `?? 0`** 을 붙입니다.
> ```ts
> const progress = report.rosarySetProgress ?? 0;
> ```

## 3. 구슬 3함수

전부 `src/hooks/useCurrentReport.ts` 에 있고, 셋 다 `patchReport` → `persist` 를 거쳐 **화면 state 와 localStorage 에 동시에** 씁니다.

### `addRosaryBead` — 한 알 채우기

```ts
const next = (report.rosarySetProgress ?? 0) + 1;
const complete = next >= ROSARY_SET_SIZE;
patchReport({
  counts: complete
    ? { ...report.counts, rosaryDecades: report.counts.rosaryDecades + ROSARY_SET_SIZE }
    : report.counts,
  rosarySetProgress: complete ? 0 : next,
});
```

| 지금 상태 | 탭 후 |
|---|---|
| 15단 · 구슬 0 | 15단 · 구슬 1 |
| 15단 · 구슬 3 | 15단 · 구슬 4 |
| 15단 · 구슬 4 | **20단 · 구슬 0** ★ |

`>=` 를 쓴 이유: 저장된 데이터가 어떤 이유로 망가져 구슬이 5 이상이 되어 있어도, 다음 탭 한 번에 정상으로 돌아옵니다.

### `removeRosaryBead` — 되돌리기

정확히 `addRosaryBead` 의 역연산입니다. 세 갈래로 갈립니다.

```ts
if (progress > 0) {
  nextProgress = progress - 1;                  // ① 구슬만 하나 뺀다
} else if (count >= ROSARY_SET_SIZE) {
  nextCount = count - ROSARY_SET_SIZE;          // ② 세트 경계를 넘어간다
  nextProgress = ROSARY_SET_SIZE - 1;
} else {
  nextCount = 0;                                // ③ 주의 (아래)
}
```

| 지금 상태 | 빼기 후 | 갈래 |
|---|---|---|
| 15단 · 구슬 3 | 15단 · 구슬 2 | ① |
| 15단 · 구슬 0 | **10단 · 구슬 4** | ② |
| 7단 · 구슬 0 | **0단 · 구슬 0** | ③ ⚠️ |

②가 핵심입니다. 세트를 완성한 그 탭을 취소하면 5단을 도로 빼고 구슬 4알이 남습니다. **잘못 누른 사람이 기대하는 그림**이 바로 그것입니다.

③은 문제가 있습니다. 직접 입력으로 7을 넣은 뒤 [−]를 한 번 누르면 6이 아니라 **0**이 됩니다. ([06-알려진-문제 §2](06-알려진-문제.md))

### `addRosarySet` — 안내 화면 완주

```ts
patchReport({
  counts: { ...report.counts, rosaryDecades: report.counts.rosaryDecades + ROSARY_SET_SIZE },
});
```

77장을 끝까지 넘긴 뒤 [기록하기]를 누르면 여기로 옵니다. 구슬과는 **별개의 입구**입니다.

> ⚠️ 이 함수는 `rosarySetProgress` 를 건드리지 않습니다. 구슬 3알을 채워 둔 채로 안내를 완주하면 +5가 되면서 구슬 3알이 그대로 남고, 이후 탭 2번에 또 +5가 됩니다. **같은 5단을 두 번 세는 경로**입니다. ([06-알려진-문제 §1](06-알려진-문제.md), [연습문제 중급 8번](05-연습문제.md))

## 4. 숫자를 올리는 입구는 두 개

```
① 홈 카드의 큰 숫자를 탭
     CounterButton → CounterGrid → page.tsx → addRosaryBead

② [기도문 보기] 창 아래쪽의 큰 버튼을 탭
     PrayerTextDialog → CounterGrid → page.tsx → addRosaryBead
```

둘 다 같은 함수로 갑니다. 갈라지는 지점은 `src/app/page.tsx` 한 곳입니다.

```tsx
const handleIncrement = (key: PrayerItemKey) => {
  if (key === "rosaryDecades") addRosaryBead();
  else incrementCount(key, 1);
};
```

②에는 배려가 하나 들어 있습니다. 첫 4번의 탭에서는 숫자가 움직이지 않아 "아무 일도 안 일어난 것"처럼 보이므로, 버튼 아래 안내 문구를 진행률로 바꿔 줍니다.

```tsx
// CounterGrid.tsx
const rosaryCaption = isRosary
  ? t("counters.setProgress").replace("{done}", …).replace("{total}", …)   // "3 / 5단"
  : undefined;
```

## 5. 구슬 그림 — BeadRow

`src/components/CounterButton.tsx` 안에 있습니다.

```tsx
<p className={styles.beads}>
  <span className={styles.beadRow} aria-hidden="true">
    {Array.from({ length: setSize }, (_, i) => (
      <span key={i} className={i < setProgress ? styles.beadFilled : styles.bead} />
    ))}
  </span>
  <span className={styles.beadCaption}>
    {t("counters.setProgress").replace("{done}", String(setProgress)).replace("{total}", String(setSize))}
  </span>
</p>
```

**그림과 글자를 둘 다 냅니다.** 채운 구슬과 빈 구슬은 색으로만 구분되는데, **색만으로 상태를 나누면 알아보기 어려운 사람이 생깁니다.** 그래서 "3 / 5단"이라는 글자를 함께 두고, 그림 쪽은 `aria-hidden="true"` 로 스크린 리더가 건너뛰게 합니다.

이 앱의 접근성 기준선이기도 합니다 — **색만으로 상태를 구분하지 않는다.**

## 6. 제출 — 구슬이 사라지는 순간

```ts
const submit = useCallback((): WeeklyReport | null => {
  if (!report) return null;
  const now = new Date().toISOString();
  const submitted: WeeklyReport = {
    ...report,
    rosarySetProgress: 0,        // ← 채우다 만 구슬은 버린다
    status: "submitted",
    submittedAt: now,
    updatedAt: now,
  };
  storage.setHistory([submitted, ...storage.getHistory()]);
  persist(null);                 // 작성 중 칸을 비운다
  return submitted;
}, [report, persist]);
```

이 함수만 `patchReport` 를 쓰지 않습니다. 제출 시각과 수정 시각이 **정확히 같은 값**이어야 하고, 구슬 버림 처리도 함께 해야 하기 때문입니다.

> ⚠️ 구슬 1~4알은 **경고 없이 사라집니다.** 제출 확인 문구에도 이 얘기가 없습니다. ([06-알려진-문제 §4](06-알려진-문제.md))

## 7. 제출 이후 — 서기에게 가는 길

```
제출된 WeeklyReport
      │
      ├─► /report 화면, 기록 목록          counts.rosaryDecades 만 표시
      │                                    (rosarySetProgress 는 어디에도 안 나옴)
      │
      └─► formatShareText()  →  카카오톡 공유 텍스트
                │
                └─► 맨 끝에 기계가 읽는 한 줄
                      LEGIO1|7|2026-08-05|홍길동|베드로|3|5|2|15|40|2026-08-05T20:31
                                                          ↑
                                                    묵주기도 (4번째 자리)
                      │
                      └─► 서기가 카톡 메시지를 통째로 붙여넣기
                            PrayerSubmissionImportDialog → 명단의 사람과 짝짓기
                                  │
                                  └─► 월례 보고서의 기도표 → 합산 → 교구 지시사항 줄
```

### LEGIO1 한 줄에서 자리가 고정된 이유

```ts
export const SUBMISSION_COUNT_KEYS = [
  "weekdayMass", "priestPrayer", "chainPrayer", "rosaryDecades", "aspirations",
] as const satisfies readonly PrayerItemKey[];
```

바로 위 주석이 이유를 못 박고 있습니다.

> 일부러 `PRAYER_ITEMS` 에서 파생하지 **않았다** — 나중에 기도 종류의 순서를 바꾸거나 추가해도, **이미 보낸 줄의 해석이 조용히 달라지면 안 되기 때문**이다.

`PRAYER_ITEMS` 는 화면 표시 순서라 언제든 바뀔 수 있습니다. 하지만 이 목록이 바뀌면 지난달에 단원이 보낸 메시지의 숫자가 엉뚱한 항목으로 들어갑니다. **화면용 순서와 전송용 순서를 분리한 것**입니다.

`rosarySetProgress` 는 이 줄에 **들어가지 않습니다.** 채우다 만 것은 보고 대상이 아니니까요.

### 월례 보고서에서

특별 대우가 없습니다. 5종을 똑같이 합산합니다.

```ts
for (const item of PRAYER_ITEMS) { sums[item.key] += counts[item.key] ?? 0; }
```

최종적으로 공식 양식의 **교구 지시사항 줄**에 `묵주기도(N)` 형태로 들어갑니다. (평일미사만 본당 줄로 빠집니다)

## 8. `ROSARY_SET_SIZE` 를 바꾼다면

`5` 를 다른 값으로 바꾸면 따라오는 곳과 안 따라오는 곳이 있습니다.

| 위치 | 따라오나 |
|---|---|
| 구슬 개수 (`BeadRow`) | ✅ |
| 5탭 = 커밋 판정 (`addRosaryBead`) | ✅ |
| 되돌리기 경계 (`removeRosaryBead`) | ✅ |
| 안내 완주 기록 (`addRosarySet`) | ✅ |
| "묵주기도 {count}단을 기록할까요?" | ✅ `{count}` 치환 |
| **"묵주기도 5단을 기록했습니다."** | ❌ **5가 글자로 박혀 있음** |

마지막 하나만 어긋납니다. ([연습문제 중급 10번](05-연습문제.md))

## 직접 확인해 보기

개발자 도구(F12) → **Application → Local Storage → `legioMariae.currentReport`** 를 열어 두고 탭해 보세요.

```
탭 전:  "counts": { …, "rosaryDecades": 0, … }              (rosarySetProgress 없음)
탭 1회: "counts": { …, "rosaryDecades": 0, … }, "rosarySetProgress": 1
탭 4회: "counts": { …, "rosaryDecades": 0, … }, "rosarySetProgress": 4
탭 5회: "counts": { …, "rosaryDecades": 5, … }, "rosarySetProgress": 0   ★
```

**중복 계수 버그 재현해 보기**:
1. 묵주기도를 **3번** 탭 → 구슬 3알
2. [기도문 보기] → 끝까지 넘겨서 [기록하기] → `rosaryDecades: 5`
3. `rosarySetProgress` 를 보세요. **여전히 3입니다**
4. 창을 닫고 **2번** 더 탭 → `rosaryDecades: 10`

3단만 더 세었는데 5단이 더 기록되었습니다.
