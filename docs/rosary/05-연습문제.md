## 1. 오늘이 목요일이면 어떤 신비가 나오나요? 근거 코드는?

<details><summary>정답 보기</summary>

**빛의 신비(`luminous`)** 입니다.

`src/lib/rosaryMysteries.ts`:

```ts
const MYSTERY_BY_WEEKDAY: MysteryId[] = [
  "glorious",   // 0 일
  "joyful",     // 1 월
  "sorrowful",  // 2 화
  "glorious",   // 3 수
  "luminous",   // 4 목  ★
  "sorrowful",  // 5 금
  "joyful",     // 6 토
];

export function getMysteryIdForDate(date: Date): MysteryId {
  return MYSTERY_BY_WEEKDAY[date.getDay()];
}
```

`Date.getDay()` 가 0(일)~6(토)을 돌려주므로 배열 인덱스로 그대로 씁니다. 목요일은 4번 자리 → `"luminous"`.

**왜 이렇게 짰나**: `if/else` 를 일곱 번 쓰는 대신 배열 하나로 끝냈습니다. 요일 규칙을 바꾸려면 이 배열만 고치면 됩니다.
</details>

## 2. 77이라는 숫자는 어떤 식에서 나오나요?

<details><summary>정답 보기</summary>

```
시작:  사도신경 1 + 주님의 기도 1 + 성모송 3 + 영광송 1              =  6
각 단: (신비 1 + 주님의 기도 1 + 성모송 10 + 영광송 1 + 구원기도 1)
       = 14, × 5단                                                = 70
마침:  성모찬송 1                                                  =  1
                                                                  ─────
                                                                    77
```

상수로는 `6 + (1 + 1 + HAIL_MARYS_PER_DECADE + 1 + 1) × DECADES_PER_ROSARY + 1`.

**직접 확인**: `HAIL_MARYS_PER_DECADE` 를 `2` 로 바꾸면 하단 표시가 `1 / 37` 로 바뀝니다. (`6 + 6×5 + 1 = 37`)
</details>

## 3. 3단의 성모송 7번째 화면은 인덱스 몇 번인가요?

<details><summary>정답 보기</summary>

**42번**입니다.

n단 블록의 시작 = `6 + (n-1) × 14` 이므로 3단은 `6 + 2×14 = 34`.

```
34  3단 신비 선포
35  주님의 기도
36  성모송 1/10
37  성모송 2/10
…
42  성모송 7/10   ★
```

즉 `34 + 1 + 7 = 42`.

**확인 방법**:
```bash
npx tsx -e '
import { buildRosarySteps } from "./src/lib/rosaryMysteries";
const l = {creed:"C",ourFather:"OF",hailMary:"HM",gloryBe:"GB",salvation:"SV",closing:"CL"};
const s = buildRosarySteps("joyful","ko",l);
console.log(s.findIndex(x => x.decade === 3 && x.ordinal === "7 / 10"));
'
```
</details>

## 4. 영어로 바꾸면 성화를 눌러도 아무 일이 없습니다. 왜일까요?

<details><summary>정답 보기</summary>

**묵상 데이터가 한국어에만 있기 때문**입니다.

`src/lib/rosaryMysteries.ts`:

```ts
explanation: ko && MYSTERY_MEDITATIONS[id]?.[d + 1] ? MYSTERY_MEDITATIONS[id][d + 1] : []
//           ↑ 영어면 여기서 곧바로 빈 배열
```

그리고 `RosaryGuide.tsx` 에서:

```tsx
const canOpenImage = Boolean(step.image && step.explanation && step.explanation.length > 0);
```

`explanation` 이 빈 배열이면 `canOpenImage` 가 `false` → `onImageClick` 으로 `undefined` 가 넘어감 → 눌러도 아무 일이 없고 커서 모양도 손가락이 아님.

**의도한 동작인가?** 반쯤 그렇습니다. 묵상 번역이 없으니 빈 팝업을 띄우느니 안 여는 게 낫다는 판단입니다. 다만 사용자에게 아무 설명이 없어 고장으로 보일 수 있습니다. → 고급 13번

## 6. "기록했습니다" 안내문이 영영 안 사라지는 문제

**재현**: 끝까지 넘겨서 [기록하기] → "묵주기도 5단을 기록했습니다." 가 뜹니다. 그 뒤로 계속 넘겨도 **모든 화면에 그대로 남아 있습니다.**

<details><summary>정답 보기</summary>

`recorded` 를 `true` 로 만드는 코드는 있는데 `false` 로 되돌리는 코드가 없습니다.

`src/components/RosaryGuide.tsx` 의 이동 함수 두 개에 초기화를 넣습니다.

```tsx
const handleNext = () => {
  if (isLast) {
    setAsking(true);
    return;
  }
  setRecorded(false);        // ← 추가
  setSlideDirection("right");
  setIndex(index + 1);
};

const handlePrev = () => {
  if (index > 0) {
    setRecorded(false);      // ← 추가
    setSlideDirection("left");
    setIndex(index - 1);
  }
};
```

**왜 이 방식인가**: "기록했다"는 알림은 기록 직후의 화면에서만 의미가 있습니다. 사용자가 움직이면 이미 확인한 것으로 봅니다.

**다른 방법**: 타이머로 몇 초 뒤에 지우는 방법도 있습니다.

```tsx
useEffect(() => {
  if (!recorded) return;
  const timer = setTimeout(() => setRecorded(false), 4000);
  return () => clearTimeout(timer);   // ← 정리 함수를 꼭 반환할 것
}, [recorded]);
```

정리 함수를 반환하지 않으면, 컴포넌트가 사라진 뒤에 타이머가 터져 없는 컴포넌트의 state 를 건드리려 합니다.
</details>

## 7. 제스처가 취소되면 화면이 비뚤어진 채로 남는 문제

**재현이 어렵습니다**: 손가락으로 밀고 있는 도중에 전화가 오거나 알림 센터를 내리면 `touchend` 가 오지 않고 `touchcancel` 이 옵니다. 그러면 인라인 `transform` 이 남아 화면이 옆으로 밀린 상태로 굳습니다.

<details><summary>정답 보기</summary>

`src/hooks/useSwipe.ts` 에 핸들러를 하나 더 추가합니다.

```ts
  /** 시스템 제스처 등으로 터치가 취소됐을 때. 넘기지 않고 제자리로만 돌린다. */
  const onTouchCancel = () => {
    if (contentRef.current) {
      contentRef.current.style.transition = SNAP_BACK_TRANSITION;
      contentRef.current.style.transform = "translateX(0)";
    }
    start.current = null;
    end.current = null;
  };

  return { onTouchStart, onTouchMove, onTouchEnd, onTouchCancel };
```

`RosaryGuide.tsx` 는 **고칠 필요가 없습니다.** 이미 이렇게 펼쳐 붙이고 있기 때문입니다.

```tsx
<section … {...swipeHandlers}>
```

객체에 키가 하나 늘면 속성도 하나 늘어납니다. 훅으로 뽑아 둔 덕을 보는 지점입니다.

**주의**: `onTouchEnd` 와 달리 넘김 판정을 하면 **안 됩니다.** 취소된 제스처는 사용자의 의도가 아닙니다.

**확인**: 개발자 도구 콘솔에서 직접 쏴 볼 수 있습니다.
```js
document.querySelector('section[aria-label]').dispatchEvent(new TouchEvent('touchcancel', {bubbles:true}))
```
</details>

## 8. ⚠️ 같은 5단이 두 번 세어지는 문제

**재현**:
1. 묵주기도 카운터를 **3번** 탭 (구슬 3알)
2. [기도문 보기] → 끝까지 넘기기 → [기록하기] → 숫자 **+5**
3. 창을 닫고 **2번** 더 탭 → 숫자 **또 +5**

3단만 더 세었는데 5단이 더 기록되었습니다. **실제 사용자에게 영향이 있는 버그입니다.**

<details><summary>정답 보기</summary>

`src/hooks/useCurrentReport.ts` 의 `addRosarySet` 이 구슬을 비우지 않습니다.

```ts
const addRosarySet = useCallback(() => {
  if (!report) return;
  patchReport({
    counts: {
      ...report.counts,
      rosaryDecades: report.counts.rosaryDecades + ROSARY_SET_SIZE,
    },
    rosarySetProgress: 0,      // ← 이 한 줄을 추가
  });
}, [report, patchReport]);
```

**왜 이게 맞는가**: 안내 화면을 완주했다는 것은 **5단을 다 바쳤다**는 뜻입니다. 그 안에는 채워 두었던 3알도 포함됩니다. 안내는 1단부터 5단까지 전부 안내하니까요.

**한 번 더 생각해 볼 것**: 정말 그럴까요? 구슬 3알을 채운 상태로 창을 열면 `initRef` 가 **4단 신비 선포 화면으로 점프**시킵니다([02장 §3](02-화면과-스와이프.md)). 즉 사용자는 4·5단만 바치고 완주한 셈입니다. 그렇다면 `+5` 가 아니라 `+2` 여야 맞습니다.

그래서 더 정확한 고침은 이렇습니다.

```ts
/** 안내 화면 완주. 이미 채워 둔 구슬을 감안해 남은 단만 더한다. */
const addRosarySet = useCallback(() => {
  if (!report) return;
  const progress = report.rosarySetProgress ?? 0;
  patchReport({
    counts: {
      ...report.counts,
      rosaryDecades: report.counts.rosaryDecades + (ROSARY_SET_SIZE - progress),
    },
    rosarySetProgress: 0,
  });
}, [report, patchReport]);
```

| 구슬 | 완주 후 |
|---|---|
| 0알 | +5 (기존과 같음) |
| 3알 | **+2** |

두 방식 중 무엇이 옳은지는 **사용자가 실제로 어떻게 쓰는지**에 달려 있습니다. 이 문서는 정답을 강요하지 않습니다 — 다만 지금 코드는 둘 중 어느 쪽도 아니라는 점이 문제입니다.

**확인**: Local Storage 의 `legioMariae.currentReport` 를 열어 두고 위 재현 절차를 밟으세요.
</details>

## 9. "동작 줄이기" 설정에서 슬라이드도 끄기

<details><summary>정답 보기</summary>

`src/components/RosaryGuide.module.css` 의 미디어 쿼리에 두 줄을 더합니다.

```css
@media (prefers-reduced-motion: reduce) {
  .heading {
    animation: none;
  }
  .slideInRight,
  .slideInLeft {
    animation: none;
  }
}
```

**왜 필요한가**: 어지럼증이나 전정기관 장애가 있는 사람에게 화면이 미끄러지는 움직임은 불편을 넘어 증상을 유발할 수 있습니다. 운영체제에 "동작 줄이기" 설정이 있는 이유입니다.

깜박임(`.heading`)은 이미 꺼져 있는데 슬라이드는 빠져 있었습니다.

**확인**: 개발자 도구 → `Ctrl+Shift+P` → "Show Rendering" → **Emulate CSS prefers-reduced-motion** 을 `reduce` 로.

> 참고: `animation: none` 이면 요소가 그냥 즉시 나타납니다. `opacity: 0` 으로 시작하는 keyframe 이 적용되지 않으므로 안 보이게 되는 일은 없습니다.
</details>

## 11. 신비를 직접 고르는 드롭다운

지금은 요일로만 정해집니다. 사용자가 "오늘은 환희의 신비를 바치고 싶다"고 해도 방법이 없습니다.

<details><summary>정답 보기</summary>

**① `src/components/RosaryGuide.tsx`** — 상태는 이미 있습니다(`mysteryId`). 바꾸는 UI 만 붙이면 됩니다.

```tsx
import { MYSTERY_ORDER } from "@/lib/rosaryMysteries";

// 라벨 매핑. 컴포넌트 밖에 두어 렌더마다 새로 만들지 않게 한다.
// Record<MysteryId, …> 라서 신비를 하나라도 빠뜨리면 컴파일 에러가 난다.
const MYSTERY_LABEL: Record<MysteryId, string> = {
  joyful: "환희의 신비",
  sorrowful: "고통의 신비",
  glorious: "영광의 신비",
  luminous: "빛의 신비",
};
```

`return` 문 안, `<div ref={contentRef}>` 바로 위에:

```tsx
<label className={styles.mysteryPicker}>
  <span className={styles.mysteryPickerLabel}>신비 고르기</span>
  <select
    className={styles.mysteryPickerSelect}
    value={mysteryId}
    onChange={(e) => {
      setMysteryId(e.target.value as MysteryId);
      setIndex(0);              // 신비가 바뀌면 처음부터
      setRecorded(false);
    }}
  >
    {MYSTERY_ORDER.map((id) => (
      <option key={id} value={id}>{MYSTERY_LABEL[id]}</option>
    ))}
  </select>
</label>
```

**② CSS** — `RosaryGuide.module.css` 에

```css
.mysteryPicker {
  display: flex;
  align-items: center;
  gap: var(--space-2);
  padding: var(--space-2) 0;
}
.mysteryPickerSelect {
  flex: 1;
  min-height: var(--min-tap-target);   /* 어르신 사용자 기준 터치 영역 */
  font-size: var(--font-size-base);
  padding: var(--space-2);
}
```

### 여기서 배울 점

- **상태는 이미 있었다.** `mysteryId` 는 처음부터 state 였고 `setMysteryId` 도 있었습니다. 요일로 정하는 `useEffect` 가 초기값을 넣어 줄 뿐이었죠. 그래서 UI 만 붙이면 됩니다. **잘 나뉜 코드는 기능 추가가 이렇게 짧습니다.**
- `setIndex(0)` 을 잊으면? 5단 40번째 화면을 보다가 신비를 바꾸면 새 신비의 40번째로 갑니다. 틀린 건 아니지만 사용자는 처음부터를 기대합니다.
- `e.target.value as MysteryId` 의 `as` — `<select>` 는 언제나 `string` 을 주므로 좁혀 줘야 합니다. `MYSTERY_ORDER` 에서 만든 `<option>` 만 있으니 안전하지만, **`as` 는 런타임 검사가 아니라는 점**을 기억하세요.

### 더 해 볼 것

- 요일 기본값으로 돌아가는 [오늘의 신비] 버튼
- 고른 신비를 `localStorage` 에 저장해 다음에도 유지 (`storage.ts` 에 getter/setter 한 쌍 추가)
</details>

## 12. 성화를 키보드로도 열 수 있게

지금 트리거는 `<img onClick>` 이라 **Tab 으로 초점이 가지 않고 Enter 로 누를 수도 없습니다.** 마우스나 손가락이 없으면 묵상을 영영 볼 수 없습니다.

<details><summary>정답 보기</summary>

`src/components/RosaryStepView.tsx` 의 이미지 부분을 `<button>` 으로 감쌉니다.

```tsx
{step.image && (
  <div className={styles.imageWrapper}>
    {canOpenImage ? (
      <button
        type="button"
        className={styles.mysteryImageButton}
        onClick={onImageClick}
        aria-label={`${step.title} — ${t("rosary.viewMeditation")}`}
      >
        {/* eslint-disable-next-line @next/next/no-img-element */}
        <img
          src={step.image}
          alt=""                    /* 버튼에 이름이 있으므로 중복을 피한다 */
          className={styles.mysteryImage}
          onError={(e) => { e.currentTarget.style.display = "none"; }}
        />
      </button>
    ) : (
      /* eslint-disable-next-line @next/next/no-img-element */
      <img
        src={step.image}
        alt={step.title}
        className={styles.mysteryImage}
        onError={(e) => { e.currentTarget.style.display = "none"; }}
      />
    )}
  </div>
)}
```

접근성 라벨(`aria-label="묵상 보기"`)은 JSX 안에 그대로 적으면 됩니다.

CSS — 버튼의 기본 모양을 지웁니다.

```css
.mysteryImageButton {
  display: block;
  padding: 0;
  border: none;
  background: none;
  cursor: pointer;
}
.mysteryImageButton:focus-visible {
  outline: 3px solid var(--color-accent);   /* 초점이 보여야 한다 */
  outline-offset: 4px;
}
```

### 왜 `<div onClick>` 이나 `role="button"` 이 아닌가

`<button>` 은 공짜로 다음을 줍니다.
- Tab 초점 순서에 들어감
- Enter / Space 로 눌림
- 스크린 리더가 "버튼"이라고 읽음
- `:focus-visible` 이 동작함

`<div role="button" tabIndex={0} onKeyDown={...}>` 로 흉내 낼 수는 있지만 직접 구현할 게 늘어납니다. **가능하면 의미에 맞는 태그를 쓰는 것**이 원칙입니다.

`alt=""` 로 둔 이유: 버튼에 `aria-label` 이 있으므로 이미지에도 설명을 넣으면 같은 말을 두 번 읽습니다.

### 함께 고칠 것

`PrayerTextDialog.tsx` 의 큰 버튼도 같은 문제가 있습니다. 화면에는 "3 / 5단"이 보이는데 `aria-label` 은 여전히 "탭하여 기록"이라, **스크린 리더 사용자는 진행률을 들을 수 없습니다.**

```tsx
aria-label={incrementCaption ?? t("counters.tapToRecord")}
```

**확인**: 마우스를 치우고 Tab 키만으로 성화까지 가서 Enter 를 눌러 보세요.
</details>

## 13. 영어 묵상 지원

<details><summary>정답 보기</summary>

지금 타입에는 **언어 축이 없습니다.**

```ts
export const MYSTERY_MEDITATIONS: Record<MysteryId, Record<number, string[]>>
```

**① `src/lib/rosaryMeditations.ts`** — 언어를 한 겹 추가

```ts
import type { Language } from "./types";
import type { MysteryId } from "./rosaryMysteries";

type MeditationsByDecade = Record<number, string[]>;

/** 언어 → 신비 → 단 → 문장들. 없는 언어는 아예 키가 없다. */
export const MYSTERY_MEDITATIONS: Partial<Record<Language, Record<MysteryId, MeditationsByDecade>>> = {
  ko: {
    joyful: { "1": [...], … },
    …
  },
  // en 은 아직 없음 — 번역이 준비되면 여기에 추가
};
```

**② `src/lib/rosaryMysteries.ts`** — 꺼내는 곳을 바꿉니다

```ts
explanation: MYSTERY_MEDITATIONS[language]?.[id]?.[d + 1] ?? [],
```

`ko &&` 조건이 사라진 것에 주목하세요. **언어가 데이터 구조 안으로 들어갔기 때문에** 코드에서 언어를 특별 취급할 필요가 없어졌습니다. 나중에 영어를 추가할 때 이 줄은 손댈 필요가 없습니다.

### 여기서 배울 점

**조건문을 데이터로 옮기기.** 원래 코드는 "한국어면"이라는 규칙이 로직 안에 박혀 있었습니다. 언어를 하나 더 지원하려면 그 조건을 찾아 고쳐야 했죠. 데이터에 언어 축을 만들면 로직은 "그 언어의 것을 꺼내라"만 하면 됩니다.

`Partial<Record<Language, …>>` 를 쓴 이유: `Record<Language, …>` 는 **모든 언어가 반드시 있어야** 합니다. 영어 번역이 없는 지금은 컴파일이 안 됩니다. `Partial` 이 "없어도 된다"를 표현합니다.

### 사용자에게 알리기 (선택)

번역이 없을 때 조용히 아무 일도 안 하는 것보다, 안내가 있는 편이 낫습니다.

```tsx
{!canOpenImage && step.image && (
  <p className={styles.imageHint}>{t("rosary.meditationUnavailable")}</p>
)}
```
</details>

## 14. 성화 선캐시 최적화

**문제**: PWA 를 처음 설치할 때 내려받는 2.83 MiB 중 **약 28%(805 KiB)가 성화 20장**입니다. 그런데 하루에 쓰이는 건 그날 신비 5장뿐입니다.

폰트에는 이미 같은 논리가 적용돼 있습니다.

<details><summary>정답 보기</summary>

`scripts/generate-precache-manifest.mjs` 에 이미 좋은 선례가 있습니다.

```js
/** Nanum Gothic ships as ~276 unicode-range slices (2.9MB). Precaching them all
    would make every install pay for a font most people never switch on; the
    runtime cache-first handler still caches whichever slices actually get used. */
function isLazyFont(relPath) {
  return relPath.startsWith("_next/static/media/") && relPath.endsWith(".woff2");
}
```

같은 방식으로 하나 더 만듭니다.

```js
/** 성화 20장 중 하루에 쓰이는 건 그날 신비 5장뿐이다(약 805KB). 첫 설치에서
    전부 받게 하는 대신, 실제로 본 것만 런타임 cache-first 로 캐시되게 둔다. */
function isLazyRosaryImage(relPath) {
  return relPath.startsWith("images/rosary/") && relPath.endsWith(".jpeg");
}
```

그리고 `walk` 안의 건너뛰기 조건에 추가합니다(`isLazyFont` 를 쓰는 곳 바로 옆).

### ⚠️ 그런데 정말 그래야 할까

**해서는 안 될 수도 있습니다.** 이건 트레이드오프입니다.

| 지금 그대로 | 지연 로딩으로 바꾸면 |
|---|---|
| 첫 설치 2.83 MiB | 첫 설치 **2.05 MiB** (−28%) |
| 어느 요일에 열어도 성화가 보임 | **오프라인 상태에서 처음 맞는 요일에는 성화가 안 보임** |

이 앱의 사용자는 성당에서 쓰는 경우가 많고, 지하 성당은 신호가 잘 안 잡힙니다. "오프라인에서도 완전히 동작한다"는 것이 이 앱의 핵심 약속입니다.

**절충안**: 그날 신비 5장만 선캐시하고 나머지는 앱이 열릴 때 조용히 미리 받는 방법도 있습니다. 다만 빌드 시점에는 "그날"을 알 수 없으므로 서비스 워커 쪽 작업이 필요합니다.

### 여기서 배울 점

**성능 최적화에는 항상 대가가 있습니다.** 숫자만 보면 28% 절감은 매력적이지만, 그 대가가 "성당에서 성화가 안 보인다"라면 하지 않는 게 맞을 수 있습니다. 최적화를 제안할 때는 **무엇을 잃는지도 함께** 적으세요.

**측정 방법**:
```bash
npm run build
node -e '
const m = require("./out/precache-manifest.json");
const urls = m.urls ?? m;
const fs = require("fs");
let total = 0, rosary = 0;
for (const u of urls) {
  const p = "out" + u.replace(/\/$/, "/index.html");
  try {
    const size = fs.statSync(p).size;
    total += size;
    if (u.includes("/images/rosary/")) rosary += size;
  } catch {}
}
console.log("총", (total/1024/1024).toFixed(2), "MiB / 성화", (rosary/1024).toFixed(0), "KiB",
            `(${(100*rosary/total).toFixed(1)}%)`);
'
```
</details>

## 보너스 — 실측으로만 드러나는 두 가지

[06-알려진-문제](06-알려진-문제.md) §16·§17 은 **코드만 읽어서는 정상으로 보이는** 문제입니다. 브라우저로 직접 재보다가 발견했습니다.

### 보너스 A. ESC 가 두 창을 함께 닫는다

<details><summary>정답 보기</summary>

`src/components/MysteryImageDialog.tsx`:

```tsx
onCancel={(e) => {
  e.preventDefault();
  e.stopPropagation();   // ← 추가
  onClose();
}}
```

네이티브 `cancel` 이벤트는 버블링하지 않지만, **React 는 자기 컴포넌트 트리를 따라 다시 전달**합니다. 그래서 부모인 `PrayerTextDialog` 의 `onCancel` 까지 불려 기도문 창도 닫힙니다.

`preventDefault()` 와 `stopPropagation()` 은 하는 일이 다릅니다.

| | 막는 것 |
|---|---|
| `preventDefault()` | 브라우저의 **기본 동작** (여기서는 dialog 자동 닫기) |
| `stopPropagation()` | 이벤트가 **부모로 올라가는 것** |

**확인**:
```js
// 성화 팝업을 연 뒤 ESC → 아래가 1 이어야 정상 (지금은 0)
document.querySelectorAll("dialog[open]").length
```
</details>

### 보너스 B. 배경을 눌러도 닫히지 않는다

<details><summary>정답 보기</summary>

판정 코드 자체는 표준 관용구입니다.

```tsx
onClick={(e) => { if (e.target === e.currentTarget) onClose(); }}
```

문제는 CSS 입니다.

```css
.fullScreenDialog { width: 100vw; height: 100vh; }
.fullScreenContent { width: 100%; height: 100%; }   /* dialog 를 꽉 채움 */
```

**어디를 눌러도 target 은 `.fullScreenContent` 이지 `<dialog>` 가 아닙니다.** 진짜 "배경"이 존재하지 않는 것입니다.

고치는 방법은 두 갈래입니다.

**(a) 진짜 배경을 만든다** — 내용을 가운데 모으고 여백을 남깁니다.
```css
.fullScreenContent {
  width: 100%;
  max-width: 640px;
  height: auto;
  max-height: 100%;
  margin: auto;      /* 위아래·좌우 여백이 곧 배경이 된다 */
}
```

**(b) 판정을 바꾼다** — 내용 영역 바깥을 눌렀는지로 본다.
```tsx
onClick={(e) => {
  const target = e.target as HTMLElement;
  if (!target.closest(`.${styles.fullScreenContent}`)) onClose();
}}
```

(a) 는 보기가 달라지고 (b) 는 동작만 달라집니다. **성화를 최대한 크게 보여 주려는 원래 의도**를 생각하면 (b) 가 나아 보이지만, 그러면 "닫으려다 실수로 눌리는" 일이 늘 수도 있습니다.

**여기서 배울 점**: 이벤트 핸들러가 옳아도 **CSS 때문에 동작하지 않을 수 있습니다.** 코드 리뷰만으로는 잡히지 않고, 실제로 눌러 봐야 압니다.
</details>
